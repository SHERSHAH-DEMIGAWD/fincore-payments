## Session 4 — Transactional Outbox and Payment Events

- **Functionality:** new payments and valid lifecycle transitions append durable payment events atomically with payment/ledger writes; creation replays and invalid transitions append none. A per-payment events endpoint exposes source envelopes and delivery metadata. An optional scheduler dispatches to a durable local PostgreSQL inbox.
- **Concepts/mechanisms:** transactional outbox, immutable versioned event envelopes, local inbox idempotency, at-least-once delivery semantics, `FOR UPDATE SKIP LOCKED`, per-payment ordering, database row-lock crash recovery, conditional retry updates, bounded exponential backoff, DEAD events.
- **Important files:** Flyway V4 (source events, delivery metadata, local inbox); payment-event domain/DTO/repository/service and read controller; outbox dispatcher/local publisher/scheduler/configuration; `PaymentService.java` (atomic event recording); shared outbox database/Testcontainers/optional-local tests; `README.md`.
- **Design decisions:** one envelope per new payment version with event UUID, payment ID/version, event type, schema version 1, occurrence time, and `PaymentResponse` snapshot. One event per dispatch transaction; local inbox receipt and acknowledgement commit together. No Kafka or external publication, historical event backfill, PROCESSING/lease state, HTTP dispatch endpoint, or requeue automation.
- **Ordering/retries:** older undelivered events block later versions for that payment; a DEAD event keeps that payment blocked while others continue. Publisher failure rolls back delivery, then a separate conditional transaction records an attempt/backoff. The limit bounds recorded failures, not all physical publisher calls: concurrency/crash windows may cause additional calls. Stable event IDs support deduplication; future external delivery may repeat an event.
- **Configuration:** scheduling defaults to disabled; `FINCORE_OUTBOX_ENABLED=true` enables it. Defaults: fixed delay 1000 ms, batch size 50, max attempts 5, initial backoff 1000 ms, max backoff 60000 ms.

## Session 9 — Isolated Shadow Projection Rebuild and Catch-Up Generations

- **Functionality:** added local `rebuild-create`, `rebuild-step`, `rebuild-status`, `rebuild-validate` and `rebuild-catch-up`. Each run owns a generated `shadow-<run UUID>` consumer identity. A materialized generation freezes one current retained source snapshot per source payment, preserving original and canonical contract evidence. Missing/invalid/disputed inputs remain explicit blocked items; consumer-only artifacts are not invented as source facts.
- **Durable execution:** bounded steps lock the run, revalidate the frozen contract and atomically commit shadow receipts, version-guarded projections, per-item checkpoints and generation state. Existing receipts require an agreeing shadow projection before progress can advance. Source/live/financial data, delivery metadata, offsets and physical consumer incidents remain unchanged. A lost response can be followed by another step without repeating committed item effects.
- **Catch-up identity:** generation 0 uses the run UUID as its accepted request ID. Later catch-up requests require the expected generation, unique request UUID and exact operator/reason; accepted repeats return the original plan result even after subsequent generations. A fresh full source manifest appends generation +1 once no pending work remains, retaining earlier decisions and coverage. New versions/new payments advance the same isolated target; blocked earlier evidence is preserved.
- **Validation:** independent read-only comparisons detect source additions/removals/content drift, missing/extra/disputed shadow artifacts and current live-consumer recovery context across source scopes. BUILT describes frozen work, while current-source agreement is a later observation. Historical completeness stays NOT_CERTIFIED and promotion remains NOT_IMPLEMENTED. A source write after validation can make that observation stale.
- **Database/transactions:** V9 adds runs, immutable generation audits and frozen manifest/progress rows. Deferred constraints reject incomplete validation, receipt-only checkpoints, missing/incorrect shadow projections and a last applied item whose generation state was not finalized. Full generation aggregates run through header checks, while per-item checks avoid full-generation rescans at every insert. Planning uses 60-second Repeatable Read TransactionTemplate boundaries with at most three complete retries for 40001/40P01; steps use 30-second Read Committed, and status/validation use 30-second read-only Repeatable Read.
